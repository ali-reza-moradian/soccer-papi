1. THE CLOCK SEAM, AND WHAT THE VACUOUS TESTS WERE HIDING
--------------------------------------------------------------------------------

THE BOMB. tests/test_maker_rt_klamci_partial_hedge.py pins NOW to the 2026-08-05
KLAMCI incident (05:58:26Z). _sweep_unregistered aged its 48h quoted scope
against the WALL clock. At 05:58Z on 08-07 the fixtures crossed 48h; by the time
it was found they were 56.5h old, so _prune_quoted emptied the scope on every
call.

TWO tests went RED. That was the harmless half.

FOUR went GREEN VACUOUSLY, and that is the half that mattered:

  test_the_sweep_alerts_but_does_not_halt          asserts halted is False
  test_the_sweep_ignores_positions_we_never_quoted asserts the sweep returns []
  test_the_sweep_is_quiet_about_registered_legs    asserts the sweep returns []
  test_the_sweep_scope_ages_out                    asserts the sweep returns []

Every one of them passes trivially against a sweep that has pruned itself into a
no-op. The sweep is the guard against the next KLAMCI — the thing that finds a
position NO registry knows about. It had silently stopped guarding, and the
suite said 1501 passed.

THE FIX. A clock seam: _sweep_unregistered(now, balances=None, now_ts=None),
defaulting to time.time(), so live behaviour is byte-identical. Tests inject
now_ts=TS. Then every "stays quiet" case got a CONTROL proving the same rig
still screams:

  * ignores-what-we-never-quoted: after asserting the out-of-scope 5000-share
    position is ignored, put an IN-scope position in the same wallet and assert
    it IS found.
  * quiet-about-registered-legs: strip the registrations from the very same rig
    and assert the very same position is now reported.
  * scope-ages-out: assert the position is found FIRST, then age the record and
    assert it is not. An empty result only means "the window closed" if you have
    shown the rig can produce a non-empty one.
  * alerts-but-does-not-halt: assert something was actually FOUND, else "it did
    not halt" asserts nothing at all.

Plus one new test that pins the seam itself: same rig, same data, clock the only
variable — found at 47h, gone at 49h.

THE SWEEP FOR THE SAME CLASS. Ran the whole suite with the wall clock shifted a
year each way. A CONSTANT offset leaves every elapsed-time delta correct, so the
only thing it can break is code comparing the clock to a PINNED absolute date.

  TIMESHIFT_DAYS=+365   1 failed, 1503 passed
  TIMESHIFT_DAYS=-365   1504 passed

Exactly ONE other hit, and it is a FALSE POSITIVE:
test_group_markets.py::test_slug_map_cache_hit_skips_network compares now_epoch
against the cache file's MTIME (catalog.file_age_hours). The shift moves the
process clock but not the filesystem. In real operation both are real, so it
cannot age out. Left alone — deliberately.

THE GENERAL GUARD. The detector is now an opt-in conftest shim (default off,
changes nothing), with that false positive documented in place:

  TIMESHIFT_DAYS=365  python -m pytest -q
  TIMESHIFT_DAYS=-365 python -m pytest -q

One command finds this whole class next time.

3. THE POLYMARKET N+1
--------------------------------------------------------------------------------

THE MEASUREMENT. Reconciliation read Poly balances one CLOB GET per token:
317-320 per pass, 175 passes, 54,065 requests in 14.6h (~1/sec sustained).
Cloudflare 429'd 6,466 of them — 12% — first at 2026-08-06 23:59:52Z (Ray
a271ff73889a0360), still firing when found. 100% on ONE endpoint:
clob.polymarket.com/balance-allowance.

WHY IT WAS NOT JUST NOISE. A 429 raises, which lands as _UNREAD. So ~12% of Poly
position reads were BLIND on every pass, and an unregistered position on a token
that happened to 429 was invisible that cycle — the exact blind spot the sweep
exists to close. Nothing halted and nothing traded wrong, which is precisely
what made it easy to file as noise.

WHERE THE 317 COME FROM. Not a leak: submit_reconcile rides the 48h _quoted
scope on the same batch (both legs of every market offered on in 48h). It is
structural, which is why the per-token shape had to go rather than the scope.

THE FIX. ONE wallet snapshot per pass, reusing the offset-paged data-api read
balance.py already had (extracted to a module-level poly_wallet_positions).
Different host — data-api.polymarket.com, not the rate-limited clob.

IT STILL FAILS CLOSED, which was the constraint that mattered:
  * wallet read FAILS      -> every token _UNREAD (never flat)
  * page walk TRUNCATED    -> every token _UNREAD (a partial wallet understates
                              every position not in it; reading that as zero is
                              the one direction of error that prunes real legs)
  * absent from a COMPLETE snapshot -> flat. The API drops rows under 0.1sh; the
                              smallest live leg is 2.12sh of tennis dust, and the
                              sweep's own floor is 0.5sh.
  * absent BUT we expect shares -> one TARGETED read rather than trusting a
                              silence, budgeted at 25/pass so a pathological pass
                              cannot rebuild the N+1. Over budget reads UNKNOWN,
                              never flat.
The sweep's own per-instrument fallback got the same budget, for the same reason.

Payload shape verified live before coding, not guessed: data-api /positions rows
carry asset (token id), size (shares), redeemable, currentValue. 180 rows, one
page, no truncation.

4. THE FALSE UNTRACKED ALARM
--------------------------------------------------------------------------------

_forget_settled_instruments dropped BOTH legs of a settled market on the premise
"the winning leg redeemed to cash (balance -> 0)". That is false in the window
between Kalshi settling and Polymarket resolving/redeeming.

26AUG07AVLBMU settled +$1.82, and about two minutes later the sweep screamed
"holding 295 shares on Polymarket that my own books do not know about" — because
the books that knew about it had just been deleted. It fired after EVERY settled
pair whose Poly leg won (26AUG06CFRTIL three times before that).

THE FIX, narrowest form: deregister a leg only once the venue says it is FLAT.
Unreadable keeps it registered — "I could not ask" may never authorise a
deregistration.

NOT "never let go": _release_settled_expected re-asks on every reconcile off the
same free wallet snapshot, so a leg goes the moment it really redeems, and it
self-heals across restarts (_expected is persisted, already_settled is
queryable).

THE ORIGINAL HANHAL PROTECTION IS UNCHANGED IN EFFECT. A worthless losing leg
keeps its _expected entry, so abs(position) - expected == 0 and there is nothing
unexplained to orphan on. Two existing tests pinned the old MECHANISM ("the leg
is forgotten"); they now pin the INVARIANT ("it is not re-orphaned, and it is
not an UNTRACKED surprise"), which is the part worth protecting.

THE ALARM STAYS SHARP. test_a_genuinely_naked_position_still_screams: a position
on a market we quoted, in NO registry, is still found, still red-alerted, and
still names the match rather than a token id.

5. THE LOG
--------------------------------------------------------------------------------

CORRECTION to my earlier report: the log is 3.3 GB, not 3.47 GB — I mis-converted
KB. The rest of that finding stands.

The HTML bodies were the visible symptom but not the bulk. httpx logs one INFO
line PER REQUEST: 4,677 of 83,690 lines in a 52-minute sample were "HTTP
Request:" — 56% of everything written.

  * third-party HTTP loggers (httpx, httpcore, urllib3, requests, websockets,
    web3, asyncio) -> WARNING. HTTP_LOG_LEVEL=INFO brings the trace back for
    debugging a venue conversation.
  * formatted lines capped at 800 chars, with "[+N chars truncated]" so the loss
    is visible. Our longest real line is the 510-char LIVE ARMED banner; a
    Cloudflare page was 8,485 bytes. Verified: a 9,000-char body truncates, a
    510-char line passes intact.
  * The offending logger is third-party (py_clob_client_v2 logs resp.text
    unbounded at helpers.py:73). The cap is in OUR config; site-packages is
    untouched.

ROTATION: 200 MB x 5 (~1 GB ceiling per component) in scripts/run_all.ps1.
Component logs are stdout piped into Out-File -Append, so nothing inside python
can own the file — the only safe moment to rename is before the wrapper that
holds it open starts. Retention reasoning: at the post-fix write rate 200 MB is
weeks per file, which covers any incident we have had to investigate, and the
REPORT_*.txt files are the durable record anyway.

NOT ARMED YET, stated plainly: rotation runs at component START, so it needs a
SUPERVISOR restart to take effect. I did not restart the supervisor — that is
the whole trading stack, and it was not worth doing unprompted for a change that
is preventive. The existing 3.3 GB file is also not rotated by this.

6c. THE N+1 HAD A SECOND ENTRANCE (found after the "0 429s" result — commit C)
--------------------------------------------------------------------------------

At 15:52:00Z — 17 seconds after the restart from the report commit — 46 fresh
429s appeared, all on clob.polymarket.com/balance-allowance, all BEFORE the
event loop's first tick. So the measurement window's zero was true but partial:
the periodic reconcile was fixed and the STARTUP path was not.

WHY. __main__ called reconcile_positions(now0) with NO batch. With balances=None
every read goes down _reconcile_read's no-batch path, which is a LIVE per-token
CLOB read. That path runs over the whole 48h quoted scope — 581 instruments —
so startup fired a burst of them. The budget added in 2e7d7c6 capped only the
FALLBACK read, never this primary one.

FIX (commit C):
  * ONE scope builder (_reconcile_scope) and ONE batched reader (_reconcile_job),
    now shared by the periodic pass AND a new reconcile_startup.
  * Startup builds the batch, so it makes ONE wallet snapshot instead of 581
    per-token reads. A failed batch degrades to the unbatched path, which is
    budgeted and therefore bounded.
  * EVERY per-instrument read in the sweep is budgeted now, including the
    no-batch primary. Over budget reads UNKNOWN — an ALERT path must never
    invent a position.

A WRONG TURN WORTH RECORDING. The first attempt had _sweep_unregistered fetch its
own wallet snapshot. The full suite went red where the files passed in isolation:
one test (test_executor.py:236) puts a signing key in the environment, and with a
key present that snapshot became a REAL network call from inside the unit tests.
The lesson is not "monkeypatch harder" — it is that reconciliation's venue I/O
belongs to _reconcile_job alone, the one place callers and tests control by
handing in `balances`. There is now a test asserting the sweep performs no wallet
I/O of its own.
