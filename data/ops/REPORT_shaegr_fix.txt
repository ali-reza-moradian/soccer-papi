--------------------------------------------------------------------------------
0. THE SHORT VERSION
--------------------------------------------------------------------------------
On 2026-08-04 the REST FILL POLL read Polymarket order 0x7b537497… , saw
``size_matched`` 116, and hedged it with 116 REAL Kalshi contracts ($29.3211).
The shares never arrived. Not late — never: the CTF balance for that token read
109.0 then, and still reads 109.0 today, and the data API has exactly ONE trade on
it, ever. The bot alerted "profit is GUARANTEED either way" over 116 naked
contracts. Over 3.5 hit and they paid $86.68 of pure luck.

``size_matched`` is set when the book MATCHES. Polymarket's trade lifecycle is
MATCHED -> MINED -> CONFIRMED and a MATCHED trade can still FAIL, and nothing
walks the field back down when it does. All three fill detectors read that field,
so this is a property of the FIELD, not of any one detector.

THE SPLIT NOW SHIPPED: hedging is a race and stays one — the hedge still fires off
the signal with no venue read in front of it. BOOKING is not a race, and now waits
for venue truth.

2. T2 — THE FIX
--------------------------------------------------------------------------------
2.1 WHAT DID NOT CHANGE

  The hedge path. A fill signal still goes straight to ``_hedge_fill`` and the
  hedge order is sent with NO venue read in front of it. This is pinned by
  ``test_no_venue_read_happens_before_the_hedge_is_submitted`` (asserts the hedge
  is the FIRST event in an ordered trace) and by a wall-clock guard.

2.2 WHAT CHANGED

  ``_defer_pair`` now stands between the hedge and the booking. It tries ONE
  confirmation read inline — that read happens strictly AFTER the hedge order has
  been sent and filled, the same place and the same reasoning as the existing
  ``_complement_shares`` re-verify of the hedge leg — and:

    * rest leg ALREADY THERE  -> book immediately, byte-for-byte as before. This
                                 is the common case and costs nothing new.
    * otherwise               -> a PENDING PAIR, retried off the loop.

  Confirmation reads the REST instrument: ``conditional_balance`` for a Poly rest
  leg, the portfolio position for a Kalshi one. The expected number is
  ``baseline + this fill's size``, where ``baseline`` is what we already believed
  we held on that instrument (``_expected_shares``, snapshotted before booking).
  On SHAEGR that is 109 + 116 = 225; the venue said 109; delivered = 0.

  DECISION TABLE

    verdict              trigger                      what happens
    ------------------------------------------------------------------------------
    CONFIRMED (full)     delivered >= fill size       book exactly as today,
                         (at any point before the     including the KLAMCI partial
                         deadline)                    logic. LOCKED alert fires.
    CONFIRMED PARTIAL    0 < delivered < fill size    book the DELIVERED-size pair
                         AT THE DEADLINE              through the same
                                                      _record_hedge_locked; pnl is
                                                      re-scaled to the shares that
                                                      arrived; the unpaired hedge
                                                      excess is unwound (verified).
                                                      Alert says what arrived.
    PHANTOM              delivered ~ 0 AT THE         no pair, no pnl, no
                         DEADLINE                     registration. The unpaired
                                                      hedge is unwound (verified),
                                                      the toll is booked into
                                                      EXITS, and a RED Telegram
                                                      names the market in plain
                                                      words. Never "GUARANTEED".
    UNREADABLE           the venue read raises        NOT a phantom. Keep waiting.
                                                      Unknown is never "nothing
                                                      arrived".

  A partial/phantom verdict is only ever reached AT THE DEADLINE. Before it, only
  a positive confirmation can short-circuit — so a slow MINED is never punished.

2.3 THE DEADLINE, AND WHY IT IS WHAT IT IS

  live.rest_confirm_deadline_s = 90.0   (new, configurable)
  live.rest_confirm_poll_s     =  2.0   (new, configurable)

  90s is ~40x the measured convergence (§1.4) and 15x the existing 6s guard. The
  error here is ONE-SIDED and the asymmetry is the whole argument: a false phantom
  verdict on a real fill would unwind a good hedge AND strand a real rest leg,
  while waiting longer costs a late Telegram. It still resolves far inside the
  5-minute reconcile. Setting the deadline to 0 disables confirmation entirely and
  re-opens this bug; that is documented at the config and in the code.

2.4 WHILE WE WAIT — THE PROVISIONAL STATE

  * caps see everything IMMEDIATELY, fail-closed: the hedge notional is committed
    stake the moment it is bought, and the fill consumes one of the day's fill
    slots up front. Only the PNL waits, and it lands via ``adjust_pnl`` — the
    established restate-without-counting-a-fill doctrine — so one venue execution
    can never consume two fill slots.
  * BOTH legs count as HELD. ``_expected_shares`` now includes pending legs. This
    is not cosmetic: without it the unwind keep-floor would read 0 and a partial
    hedge's remainder sell would liquidate the sub-pair it was just paired with
    (KLAMCI, again), and the account fill sweep would see a hedge nobody claimed
    and halt on it (HANHAL, again).
  * nothing is booked, alerted, registered in the durable expected-position file,
    or paid out as edge.

  THE EXISTING PROVISIONAL-MARKS MACHINERY WAS NOT REUSED, deliberately. That
  machinery books a WORST-CASE PNL now for an open position and rebooks it at venue
  truth on settlement. A pending pair has no pnl booked at all and lives ~1-90
  seconds. Forcing it through that path would mean writing, and then reversing, a
  number we have no reason to believe. Noted here because the prompt asked for it
  "if it fits", and it does not.

2.5 THE PHANTOM UNWIND, AND WHY THE KEEP-FLOOR MATTERS HERE

  The unwind runs against the HEDGE instrument, driven through a ``dataclasses``
  view of the order whose rest side IS that leg — so it reuses ``_verified_unwind``
  unchanged, keep-floor and all. On SHAEGR the same Kalshi ticker also held the 109
  contracts of the EARLIER, genuine pair: the venue reads 225, we sell 116, and the
  keep-floor stops the reconcile-to-flat loop at 109. Without the KLAMCI fix from
  the previous commit, this fix would have liquidated a good pair. Pinned by
  ``test_shaegr_replay…`` (asserts positions end at exactly 109.0).

  The pending record is POPPED BEFORE the unwind, so the pair being unwound is not
  counted among the shares we hold on purpose.

2.6 IDEMPOTENCE

  All detectors funnel through ``_on_fill_detected``, which acts only on an
  INCREASE over ``matched_seen``; ``_defer_pair`` runs inside that one path and
  returns synchronously, so ``matched_seen`` still advances exactly as before and
  no detector can re-route the same delta. The off-loop worker de-duplicates
  confirmation reads on ``("rest_confirm", pair_id)``. ``_resolve_pending`` pops
  before it acts, so a late duplicate result is a no-op. Pinned by
  ``test_all_detectors_seeing_the_same_phantom_produce_ONE_hedge_and_ONE_unwind``.

2.7 THE OFF-LOOP SHAPE

  Confirmation is ONE venue read per pending pair per cadence, submitted to the
  shared worker — never a blocking poll. A 90s polling loop on that thread would
  black out the fill-poll backstop, which is the 2026-07-30 starvation incident.
  A backstop decides a pending pair from its last read if NO confirmation result
  ever lands (deadline + 30s grace), so a starved or abandoned worker cannot leave
  real money hedged against nothing with nobody looking.
